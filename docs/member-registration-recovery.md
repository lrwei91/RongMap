# 成员注册失败与重试恢复

## 根因与证据

用户名注册原先依次创建 Auth 账号、写入 `profiles`、写入 `space_members`。数据库步骤失败后，账号仍然存在；下一次请求仅按 Auth 邮箱判重，导致成员列表没有这个人却提示已注册。

本次只读诊断确认了一个 Auth 账号存在但两个业务表都没有对应行的状态。生产运行日志中记录了 `profiles` 写入被 RLS 拒绝，错误代码 `42501`。数据库的服务端角色有该表的读取、插入和更新权限，问题来自客户端会话，而非缺少表权限。

`/api/v2/session` 原先调用共享管理员客户端的 `signInWithPassword`。即使关闭会话持久化，SDK 仍在客户端实例内维护用户会话，后续数据库请求采用用户的 Authorization，不能继续作为管理员执行跨成员资料写入。这与 [Supabase 关于管理员客户端 RLS 错误的说明](https://supabase.com/docs/guides/troubleshooting/why-is-my-service-role-key-client-getting-rls-errors-or-not-returning-data-7_1K9z)一致。

## 修复范围

- 每次登录创建独立客户端；管理员客户端只承担服务端身份验证、空间成员检查和数据库管理操作。
- 新建账号时写入由服务端控制的 `app_metadata.rongmap_registration_space`。资料或空间成员写入失败后，管理员再次提交同一用户名可继续完成本空间的注册，无需删除账号或修改密码。
- 完成的注册重复提交返回现有成员资料，不覆盖姓名或成员角色。成员关系写入忽略已有记录，避免并发重试覆盖角色。
- Auth 查询按页检查；仅将明确的账号重复错误判为冲突，不把所有 422 校验错误都当成用户名重复。
- 不自动接管其他空间的账号，也不依据可由用户修改的 `user_metadata` 授权恢复。历史半成品账号缺少可信归属标记时，提示管理员修复。
- 非关键活动记录失败不会把已完成的注册变成失败响应。数据库失败日志只输出诊断代码，不输出失败行的私人字段。

## 验证与线上边界

86 项单元测试通过，其中新增回归覆盖资料写入失败、成员关系写入失败、重复提交、角色保留、并发账号创建冲突、Auth 分页、历史半成品账号及跨空间拒绝恢复。SDK 请求测试通过模拟 HTTP 响应执行真实登录接口，检查登录之后管理员数据库请求仍保留管理员 Authorization。

登录与注册界面的 4 项本地 Chromium 回归通过，生产构建与服务器脚本检查通过。浏览器使用模拟 API，没有通过测试创建真实账号。生产构建仍有主包超过 500 kB 的已有警告。

用户明确确认后，已在单个数据库事务中为目标半成品账号补齐个人资料与当前共享空间的普通成员关系。写入前重新确认账号存在、两张业务表中均无对应记录、项目只有一个空间且只有一位空间管理员；写入没有删除账号、修改 Auth 账号或重设密码，也没有赋予管理员角色。写入后通过 SQL 及项目成员列表使用的关联查询确认成员可见、资料完整且角色为普通成员；未代替该成员执行真实登录。代码修复的提交、推送及部署未在本次账号修复中执行。
