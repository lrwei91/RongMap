# 成员注册失败与重试恢复

## 根因与证据

用户名注册按顺序做三件事：创建 Auth 账号、写入 `profiles`、写入 `space_members`。数据库这一步失败后，账号已经留下；下一次请求只按 Auth 邮箱判重，于是成员列表里没有这个人，界面却提示已经注册。

只读诊断确认了一个这样的账号：Auth 账号存在，两张业务表都没有对应行。生产运行日志记录了 `profiles` 写入被 RLS 拒绝，错误代码 `42501`。数据库的服务端角色对这张表有读取、插入和更新权限，问题出在客户端会话，不是缺表权限。

`/api/v2/session` 调用共享管理员客户端的 `signInWithPassword`。即使关掉会话持久化，SDK 仍会在客户端实例里维护用户会话，后续数据库请求带着用户的 Authorization，没法继续以管理员身份跨成员写资料。这与 [Supabase 关于管理员客户端 RLS 错误的说明](https://supabase.com/docs/guides/troubleshooting/why-is-my-service-role-key-client-getting-rls-errors-or-not-returning-data-7_1K9z)一致。

## 修复范围

- 每次登录创建独立客户端。管理员客户端只负责服务端身份验证、空间成员检查和数据库管理操作。
- 新建账号时写入由服务端控制的 `app_metadata.rongmap_registration_space`。资料或空间成员写入失败后，管理员用同一用户名再次提交，就能继续完成本空间的注册，不需要删除账号或修改密码。
- 已完成的注册重复提交时返回现有成员资料，不覆盖姓名和成员角色。成员关系写入会忽略已有记录，避免并发重试覆盖角色。
- Auth 查询分页检查，只有明确的账号重复错误才算冲突，不把所有 422 校验错误都当成用户名重复。
- 不自动接管其他空间的账号，也不依据用户可自行修改的 `user_metadata` 授权恢复。历史半成品账号缺少可信归属标记时，提示管理员修复。
- 非关键的活动记录失败，不会把已经完成的注册变成失败响应。数据库失败日志只输出诊断代码，不输出失败行的私人字段。

## 验证与线上边界

86 项单元测试通过。新增的回归覆盖资料写入失败、成员关系写入失败、重复提交、角色保留、并发账号创建冲突、Auth 分页、历史半成品账号和跨空间拒绝恢复。SDK 请求测试用模拟 HTTP 响应执行真实登录接口，确认登录之后管理员发出的数据库请求仍保留管理员 Authorization。

登录与注册界面的 4 项本地 Chromium 回归通过，生产构建与服务器脚本检查也通过。浏览器用的是模拟 API，没有通过测试创建真实账号。生产构建仍有一个已有警告：主包超过 500 kB。

用户明确确认后，已在单个数据库事务里为目标半成品账号补齐个人资料和当前共享空间的普通成员关系。写入前重新确认了账号存在、两张业务表都没有对应记录、项目只有一个空间且只有一位空间管理员；写入没有删除账号、没有修改 Auth 账号、没有重设密码，也没有赋予管理员角色。写入后用 SQL 和项目成员列表使用的关联查询确认成员可见、资料完整、角色为普通成员；没有代替该成员执行真实登录。代码修复的提交、推送和部署不在那次账号修复范围内，当时没有执行。
